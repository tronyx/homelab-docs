# Kofax Monitoring

## Queues\Modules\Processes Overview

Queues, Modules, or Processes are essentially the queues that each Batch goes through when processing through Kofax. They are broken down into 2 categories:

- **Attended\Manual** - The Batches sit in these queues awaiting manual input from the Operations Team.
- **Unattended** - These run automated processes that do a number of different things.

Some of these are “Standard Kofax” meaning they are pre-packaged and installed when installing Kofax. Others are custom built by Iron Mountain and get installed separately.


### Kofax - Unattended

- **Recognition Server** - Reads T-Patch sheets and splits out documents(primarily in Color and Grayscale scanning). Also does a barcode read if designated within the Batch Class.
- **PDF Generator** - Since Kofax natively stores all temp images in .tif format. If the desired output of the Batch is a PDF then this process converts those single page TIF images into multipage .pdf documents based on document separation. 
- **Export** - Takes the final outputted file from the temp location and moves it to the designated “release” location within the configuration. Depending on configuration it can also generate text based files that include multitudes of information pulled from the Batch itself (image counts, doc counts, index information, date and times, etc).
- **XML Import Connector** - Is a service that is installed as required. It takes a pre-populated .xml along with “temp images” and imports said images into Kofax. The .xml file is usually generated by a another application and has the data required for Batch creation\import (Batch Class, SKP Box Number, Batch Name, etc).
- **KIC (Kofax Import Connector)** - Similar to the XML Import Connector, but more robust and more options. This is primarily used by use to import “emails” from a specified mail box into Kofax. Requires a lot of additional set up by the Dev team.

!!! note

    In most of our “newer” Batch Classes the PDF Gen and Export queues are not utilized. Generally it’s preferred to use our custom equivalent scripts which are more robust and offer more options.


### Kofax - Attended

- **Scan** - Initial phase of Kofax. When a Batch is created via Batch Manager or within the `scan.exe` process the Batch is then opened and images scanned. Upon completion the Batch must be closed and show up in the history as “Scan Complete” otherwise it will error out.
- **Quality Control** - Normally the second manual phase of operation. The purpose is to allow the operational team a chance to review the images before going off to be indexed. “Bad” images or other issues will be corrected here. If there are too many issues then the Batch will be rescanned.
- **Validation** - First round of indexing. Data either found on the image, folder, or some where else is entered in during this process that identifies each individually released file. What is indexed, how many fields, and where that data is placed after the Batch leaves Kofax can vary greatly and is dependent on the Batch Class design.
- **Verification** - Second round of indexing. This is where a second user (not the same as the first to minimize possible errors) goes back through and re-indexes some(or all) of the data captured during Validation to ensure accuracy.


### Integration Modules - Unattended

- **IM Integration Modules** - Ranging from 1 to 66 they all serve different purposes based on what the Dev wants it to do for that specific Batch Class. The modules are set up on each server as a service (for the v2 there is a single service that controls all the sub processes), then when a Batch goes to that queue in Kofax the service picks up that Batch, goes out to a shared “scripts” folder and pulls it’s instructions from a Custom.xml file that tells that service what it needs to do during that process. Technically ANY module number can be used for any number of purposes, but I’ll list some of the more common modules below and what each one does.
    - **3** - Generally used for “Release”. Similar to Kofax’s “Export”. In newer Batch Classes this may also do .pdf conversion as well.
    - **6\66** - In the commercial environment it is used to assist with “syncing” issues when using CTERA to sync files from the local environments to the central environments. 
    - **7** - Converts .tif files into .pdf using GDPicture (third part conversion tool).
- **GDS Capture Recognition** - Used for barcode reading.
- **GDS Capture PDF** - .tif to .pdf conversion using GDPicture (third part conversion tool).
- **GDS Capture Release** - Used similarly to Kofax’s “Export” services or IM3. Exports the images and creates custom report files based on customer requirements.


### Integration Modules - Attended

- **IMQC** - Customer quality control module. Uses KWIC interface to assist in either comparing sets of images or doing some other advanced work during the Quality Control process that isn’t available in the Kofax "Quality Control” program.
- **KWIC Validation\Verification** - Similar to Kofax’s Validation and Verification, but with some advanced features like Database look up, refining field hierarchy and other things.
- **SHERPA Validation\Verification** - Still used for standard indexing, but is designed as a sort of “one stop shop” for Batch Classes. Utilizes a “SHERPA Barcode” sheet at the beginning of the Batch to tell the system what index and release values to use. Essentially allowing you to run multiple projects for multiple customers from a single Batch Class separated by use of the SHERPA barcode sheet.
- **GDS Capture Validation\Verification** - Essentially SHERPA v2. Used exactly the same way, but with updated information and a central web ui where implementations can go and create\configure jobs to be used.


### Integration Modules - Other

These are services\programs that are commonly “associated” with Kofax, but are not required for Kofax to function. 

- **IMShort** - This service is usually set up on the same server we have our Webstatus and other reports on. The primary purpose of IMShort is to take the .TRK (Tracking files) that come out of Kofax and ingest them into a SQL Database so the data can be referenced later. However IMShort is essentially an Iron Mountain based service that can run any .cs script created for it to do a multitude of things.
- **Webstatus\Reports** - An IIS server set up to allow visualization of the database that IMShort is writing the TRK file data to. Each site\project will have their own landing page for the local operational team to utilize. From there they can run any number of reports (specific queries on the database) to pull information they require for the project. “Webstatus” specifically is a query for viewing the status of each Batch within Kofax. Managers\Supervisors\Team leads utilize this when they are not allowed to have Kofax Batch Manager on their local station.
